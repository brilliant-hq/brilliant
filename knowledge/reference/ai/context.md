# Context and Attachments (Explicit Consent)

Outbound chat traffic is **explicit-consent only**. Brilliant does not auto-attach screenshots of the screen, system info, app version, recent files, telemetry, or other ambient context. The default is to send nothing extra beyond your prompt.

Context that can travel with a message:

1. **Canvas context (a text outline):** the first message of a chat carries a short *text* orientation: the canvas name, the top-level frames with their child counts (no element tree), the design-system token catalog, the component catalog, and the element count at session start. It goes with the first message only, on every provider (later messages add just a one-line note when the user switches canvases, or the new token catalog when the design-system picker changes). The model reads the elements it works on through `read` and `get_selection`, and each `<edit>` block's result tells it what changed, including when an element it had read was changed or removed by someone else in the meantime. This is text, not an image; no screenshot of the canvas or screen is captured for this context. Your current *selection* is not included here; send it explicitly with an `@` element attachment or via the `get_selection` tool. A very large selection (past 1,000 elements, descendants included) reaches the model as a summary: the count, the counts by type, the bounds, the first 100 ids and the top rows, and the model reads any part of it in full with `read`. To send a prompt with no canvas context, start the chat in an empty workspace.
2. **Per-message attachments (opt-in):** each shows as a chip above the input with an X to remove before sending. Nothing attaches unless you add it. An **element** attachment (via `@` or paste) sends that element's Blueprint plus a PNG render of just that element; **image / file** attachments send what you added. Pasting into the chat input attaches what you copied and never places anything on the canvas: a copied image attaches as an image, and files copied in Explorer or Finder attach exactly as if you had dropped them on the chat (images as images, other files as file chips). The chat input's right-click Paste works the same way for a copied image or file. After sending, the same chips stay under your message in the chat: hover an image chip for a larger preview, click it to place the image on the current canvas and zoom to it (a second click selects the image it placed instead of adding a copy), and click a file chip to open the file. An image goes to the model as PNG, JPEG or WebP: a GIF, BMP or other image is converted first (an animated GIF sends its first frame), and a file that cannot be read as an image is left out with a notice naming it while the rest of the message is sent. If the AI provider still cannot read an attached image, the turn stops with a line naming the image, the image is removed from the chat, and sending again works without it. An attached **PDF** goes to the model as a document on Brilliant AI, Google and OpenRouter (up to 10 MB; a larger or unreadable one is named by a line in the chat and the rest of the message is sent). With other providers on desktop, the model reads attached files (PDFs included) through its file tool, as before. **On the web**, the chat attaches images, PDFs and text files (code, Markdown, CSV and the like, up to 10 MB each); any other type is refused with a notice, and a PDF sent to a provider that cannot read it is named by a line in the chat while the rest of the message is sent. A web attachment lives only in the open tab: after a reload the model can no longer read a text file from an earlier message, so attach it again.
3. **Automatic self-review screenshot (after edits):** after each block of changes, the AI reads that block's result before it does anything else: what landed, notes, and a screenshot of *those changed elements*. It asks for the result itself, or Brilliant hands it over before the AI continues; then it checks its own work (spacing, contrast, alignment, clipping). It is a render of the design content only, never the screen or other apps. Text-only models never receive it, and it is suppressed for the rest of a session once an endpoint rejects image input. After two blocks in a row that change nothing new, Brilliant asks the AI to wrap up with an overview instead of opening another block.

| Attachment | How to add |
|------------|------------|
| Element | Type **@** in the chat input and pick an element by name (its structure and a render are attached) |
| Image | Paste (Cmd+V), drag-and-drop a file, or click the paperclip |
| File | Drag-and-drop into the input, or click the paperclip |

When suggesting outbound workflows (sending logs, repro steps, feedback), follow the same rule: never auto-attach screenshots/version/files; ask per item; default to none.

## What the AI Can Do on the Canvas

Once a session is running, the model can create and modify designs and call tools.

- **Create designs:** build full UI, pages, dashboards, illustrations, diagrams, and wireframes that appear on the canvas as native, editable elements.
- **Edit existing work:** inspect the current design, change properties, reparent, rename, delete, and reorder elements.
- **Run app commands:** the AI can invoke Brilliant commands (align, distribute, flip, corner radius, opacity, blend mode, tool changes, frame and component operations, and more, over 100 in all). Each runs through the same path as a button or shortcut, with full undo.
- **Use selection and search:** read the current selection and look up elements by name, text, type, color, or component.
- **Export:** render selected elements to raster (PNG, JPEG, WebP), vector (SVG, PDF), HTML/React markup, or video (MP4, MOV). Raster comes back as an inline image, SVG/HTML/React as text, and PDF as base64; video (and any `outputPath`) writes a file and returns its path; an HTML/React export to a file also writes its pictures under `images/` beside it (`htmlImages: "inline"` embeds them instead). In the web editor there is no local filesystem, so `outputPath` is refused (omit it and the data returns inline) and video export is unavailable. Replay is the one export the tool cannot do (it needs an interactive recording session), so it is UI-only.
- **Read and write files / run shell commands / search the web:** when working in a real project workspace (these are most capable in the Claude CLI path). In the web app (browser) there are no shell or file tools and no external MCP servers; `web_fetch` and every canvas tool work normally, and exports come back inline (raster as an image, SVG/HTML/React/PDF as text); video export is unavailable in the browser (it needs the native desktop encoder).
- **Generate images and vectors:** see `reference/ai/images` and `reference/ai/vectors`.
- **Background work and sub-agents:** for large tasks the AI can run shell commands in the background and launch helper agents, in parallel or in the background. A strip above the input lists what is running, each with Stop: a shell row expands to its live output, and a sub-agent row opens that sub-agent's conversation, with a **Main chat** row to go back. When background work finishes, the chat picks up by itself under a row naming what finished. A finished sub-agent stays in the chat as a card (name, done, failed or stopped, tool uses, tokens, duration) that opens its conversation. This works the same on Brilliant AI, your own keys and the Claude CLI; sub-agents are not available on the Codex backend. On the Claude CLI, a multi-step plan shows as one **Plan** card that ticks off as the AI works.

On a **view-only project** (a cloud project opened without edit access, or one being viewed while signed out), the canvas-changing tools are refused with a message to sign in; reading, searching, inspecting the selection, and exporting keep working. Signing in with an account that can edit, or downloading a copy to work on locally, makes the tools available again. On a public project you can view but not edit, `create_canvas`, `duplicate_canvas` and `create_structure` still run, but the canvas exists in this session only: they answer `saved: false`, `lostOnQuit: true` and a note that edit access to the project is what would save it.

The full canvas-authoring grammar (Blueprint DSL) and the command/tool catalog are documented for the AI in the blueprint knowledge files (`blueprint/*`, including `blueprint/commands` for the command catalog); users do not author that syntax by hand.

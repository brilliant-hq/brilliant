# Helping with a Figma import

When a user says their Figma import has issues, the facts are in three places, and you can read two of them yourself:

1. **The Migration report**: a canvas named `Migration report` at the project root (unnumbered, last in the canvas list), written at the end of every import run and rewritten in place on every re-import and whenever a library pairing ends later. It is the record of what arrived, what degraded and what stayed a copy. Read it first.
2. **The app log**, desktop only: `~/.config/brilliant/logs/brilliant.log` holds every import issue, one line each, under a header naming the file, the door and the canvas; the report folds a page at 12 distinct warnings and sends you here for the rest. The web editor keeps no log file: there the row points at the browser console, which only the user can open.
3. **The run page and its Done page** in the app, which only the user sees: the pages that did not land (red rows with Retry), the end notes and the fonts card. Ask the user what the Done page said when the report does not explain the symptom.

## Reading the report from an agent

- Find it with `execute_commands` `get_canvases` (no `canvasId`): the canvas named `Migration report` at the root. A project with no such canvas was never imported with the plugin's Import to Brilliant, or the run never reached its end (the report is written when the run ends, complete or not).
- Read it with `read`, `scope: ["Migration report"]`, `format: "blueprint"`: the report is a column of plain text frames, one frame per section, and the text rows carry every sentence. `summary` gives the frame names only.
- Never edit the report: the next run rewrites the whole canvas, and your text would go with it. Nothing you change elsewhere in the project changes the report until the next run or pairing rewrites it.

## What each section says

Every section of the report in order, what it means and the kept-as-copies reasons with their remedies: `reference/canvases/figma-import-report`.

## Remedies, by what the user reports

Each remedy names the tool that runs it. Everything that happens inside Figma (the plugin's Import again, Resume, Retry, Cancel import, Connect Figma) is the user's act: the plugin talks to Brilliant, not to you, and none of those are commands an agent can run. Say so plainly and tell them exactly which button.

- **"The fonts are wrong" / texts shown in a substitute.** Read the canvases (`read`, `format: "blueprint"`): a substituted text's row keeps its true family and carries a whole-text span `spans[(0,N,sub(<substitute>))]`, so you can list every text in a given family. To change them, `execute_commands` `set_font_family` with `ids` (text elements, or frames: their text descendants) and `{"value": "<family>"}`: one act per family, undoable, and it clears the substitute stamp, which is what the inspector's Replace does. Prefer a font Brilliant can serve (a bundled font, any Google Font, or a font installed on this computer). To get the real font back instead, the user installs its `.ttf` or `.otf` files: `install_font_files` opens that file picker for them (desktop), and installed fonts switch back in place without a re-import. Outlined icon fonts are different: install the font, then the user imports the file again to get editable icons. The palette's "Replace missing fonts" lists every substituted font in the project with a picker per font; that page is the user's, not yours.
- **"My components are copies, I wanted them linked."** Read the two library sections. Copies because the library is not connected: the user imports the file again (Update is preselected) and picks the library on the Libraries step: **Use your library** for one they own, **Use your team's library** for a team's, **Use the shared library** or **Use @owner's library** for one another account shares with them, **Use the public library** for one Brilliant hosts, or **Use <name>** after Pick a different library; the pages are converted in place and the report is rewritten. Copies with a reason heading: the reasons table in `reference/canvases/figma-import-report`. An agent's `add_library` adds a library to the project and fetches it, but it does not pair standing copies with that library's components: that pairing runs from the Libraries step, at the end of a run, when a library download that was owed lands, and when the user picks a library on the screen of an already imported project. So for linking, send the user to the import screen; use `add_library` / `update_library` only for the remedies that name them.
- **"Make these copies a library."** A project whose imported components are copies becomes a library in one act: `mark_project_as_library`, then `create_library_release` (the first release is `1.0.0`): the copies are adopted as the library's own components, other projects can add it, and a later import of the same Figma file recognizes the library by its component keys. Two conditions, say them first: the adoption happens only when every component the project holds is such a copy (a project with components of its own keeps the distinction and leaves the copies out of its release, `reference/libraries/publishing`); and the acts need a producer lane, which on the desktop means the project is published to the account first (a local-only import has none: publish it in Settings, Project tab, then mark and release) and in the browser means the account can admin the project. The Done page's own "Make this a library" note stands under the same conditions. On the Free plan the library is public; say so before acting. Owner or team manager only; the refusal names it.
- **"A library could not be downloaded" / the Linking libraries step ended red.** The import is done and the components stay copies. The download retries by itself (every 15 seconds at first while offline, then less often), the user's Try again on the library's row in the Assets view fetches it now, and opening the project again does too; once it lands the pairing runs by itself and the report is rewritten. Nothing to do from your side.
- **"Linking took too long, the copies were kept."** The pairing has a ten minute budget per library. What was linked stays linked; importing the file again retries the rest.
- **Component references that do not resolve.** The row names the master, its instances and the canvases, and the repair line says which case it is. "Re-pointed at the master of the same name on <canvas>": done already, nothing to do. "A master of the same name exists on <canvas>; re-point these instances" (the master is in place and the instances still carry an old id, also the "replaced during the import" case): there is no row that re-points an existing instance, so either the user imports the page that defines the master again (the instances reconnect), or, on their word, you replace each stale instance: `read` it (`format: "blueprint"`, its position, size, variant and overrides), write a fresh `inst(Name, canvas(path))` with the same `p()` and `at()` in an `edit`, then delete the stale one (`blueprint/components`). "Masters with this name exist on N canvases": ask the user which one, then the same replacement. "These instances have no master in this project": the user imports the page that defines it. `parent(#master, canvas(path))` is for a master that must MOVE to another canvas (every instance is re-pointed in one undoable step); it is not a repair for instances that lost their link. `detach_component` with `ids` turns an instance into a plain frame that looks the same, for a user who no longer wants it to follow a master.
- **A page did not land** (the header's `n of m`, a red row in the app). The user presses Retry on the run page, or opens the plugin in that file and presses Import to Brilliant again with only that page picked: it converges onto the same project. In the browser, a page refused for its size ("too large to import in the browser") lands only through the desktop app. Nothing you run re-sends a page.
- **The import was interrupted** (the plugin closed, Figma quit, Brilliant quit). The user reopens the plugin in the same file: it reads "Import in progress: N of M pages landed" with Resume, which lands only what is missing into the same project; Start over begins afresh. Nothing already landed is imported twice. Only the user can press it.
- **"Connected to an older Brilliant"** on the plugin, or a plan the plugin refused for a Brilliant older than it expects. The desktop app is older than the import screen. Plugin 1.7.2 and later shows "Get the latest Brilliant" under that line, which opens the download page; on desktop you can also run `check_for_updates`, which opens Settings > About, where the app checks for an update and offers the install. Importing in the browser is always current, so the line never shows there. Until the update the plugin shows its older panel and imports the way it always did.
- **"Figma could not resolve a component" in a page's warnings** (a nested icon from a library the account cannot open, a deleted master). The layer landed as a plain frame. The fix is in Figma: connect an account that can open that library (palette, Disconnect Figma then Connect Figma, the user's act) and import the page again; a library pairing then stops reading that component as different.
- **Pages the user renamed or moved** are not an issue: a re-import matches pages by their Figma identity, so renamed and moved canvases are refreshed in place.
- **"My own edits on an imported canvas disappeared."** A refreshed canvas becomes what its page holds in Figma now. The work is in the project's checkpoints and recovery if it was saved (`reference/canvases/recovery`); for the future, keep hand work on canvases of your own or leave that page unpicked on the Pages step.

The agent lane also has `import_figma` (a file or page by URL over Figma's API, `blueprint/commands`): it lands a plain import into a folder named after the file, with no design-system variables and no library wiring, and it never refreshes the screen import's canvases. It is not a remedy for a plugin import; use it only when a user asks for that lane by name.

# The Migration report, section by section

Where the report is, how an agent reads it and the remedies per issue: `reference/canvases/figma-import-help`.

In order, top to bottom. A section that has nothing to say is absent, so a short report is a clean one.

- **Having trouble with this import?**: the first card is a note to the user about you ("Ask your agent in Brilliant. It can read this canvas, explain each note, and fix what it can, such as the fonts of substituted texts or instances that lost their master. For the rest it tells you exactly what to press."). It is not an issue; skip it.
- **Header**: `"<file>" imported from Figma · n of m pages landed`. `n` below `m` means pages are missing: cancelled, refused, or they never arrived (see "A page did not land" in `reference/canvases/figma-import-help`).
- **Summary**: three counts, pages imported, elements created, warnings. "warnings (all clean)" is only written when the whole report is clean.
- **Optimized n oversized images**: Figma serves full-resolution originals and the import keeps only the pixels the placement needs. Information, nothing to do.
- **n of m images did not finish uploading** (browser imports only): the images are kept in an outbox and retried on their own; opening the project again in the same browser finishes them.
- **Imported with only the variants in use: '<set>' (n of m variants)** (browser imports only): a big component set is sent ahead of the page that uses it, and that send did not land, so the project holds only the variants the pages use. Re-importing the named page brings the whole set; nothing else is lost.
- **Pages**: one line ("All n pages imported cleanly." or "k imported cleanly, j need a look."), then one card per page with `<elements> elements · <warnings> warnings` and the warnings as bullet lines (a page's 12 most distinct; "+ N more on this page. The full list of this import is in the app log.", or "in the browser console." in the web editor). A warning names a layer and what the import could not keep (a paint it cannot draw, a style Figma did not hold, a component Figma could not resolve). Most are information: the layer landed as close as Brilliant can draw it.
- **Pages that changed in Figma**: canvases from an earlier import that no longer match a page of the file (renamed or removed in Figma). Brilliant never deletes a canvas on a re-import; the user decides. If they want them gone, `delete_canvas` with the canvas's `fullPath`, one per line of the section, on their word.
- **Missing fonts**: one line of counts, then one row per family with how it degraded:
  - "shown in <substitute>": a text font this computer cannot serve, drawn in a close open font (`reference/canvases/figma-import-run`, "Fonts") with the true family kept, so the text stays editable. "(your pick)" means the user chose that substitute before.
  - "drawn at the nearest weight (n weights missing here)": the font is installed, a weight the file uses is not.
  - "drawn as outlines (icon fonts have no substitute)": a private icon font came in as pixel-true glyph outlines; the layers are named "... (outlined: FontName)".
  - "icon glyphs not rendered (blank/placeholder boxes)": only on a URL import, where the glyph geometry is not available.
  - "missing in the Figma file": Figma itself reports the font missing in the source; the family is kept and counted.
  The section ends with the guidance the Done page carries too (Replace missing fonts, Install Font Files, outlined icon fonts need a re-import). Brilliant never downloads commercial fonts.
- **Component references**: the audit that every instance the import re-pointed at a master on another canvas still resolves. Clean: "All n component references across m canvases resolve to a master in this project." Otherwise one row per master that is missing, with its instance count, the canvases affected and one repair line: re-pointed already ("Re-pointed at the master of the same name on <canvas>"), a same-name master exists elsewhere, several candidates on several canvases (Brilliant did not choose), or no master at all ("Re-import the page that defines it, or re-attach them by hand"). Instances keep their content either way; they only stop following a master.
- **Libraries already in Brilliant**: Figma libraries the file uses that are already library projects in Brilliant ("@owner's library <name>" for a cloud library, "your library <name>" for one on this disk), and whether this project is linked to them. Information.
- **Components from other Figma files**: the components the file uses from Figma team libraries, one card per library as the Figma file names it, each component with its instance count, and "· N property sets (names)" on a copy whose boolean or swap properties were factored: each is a small component set named `<component> / <property>` standing beside the copy on the Components canvas, so the canvas holds more masters than the file had components; the copies line counts them too ("with N property sets beside them", also after "k kept as copies" on a library matched by structure), and a set is stated once: it is never listed again as a reason of its own. They are not orphans: never delete them, and `mark_project_as_library` adopts them with their masters. The card's line is the outcome: "n components (m instances) linked to <library>" (the instances are live library components), "... linked to <library> by structure, k kept as copies" (a library matched by name and structure because Figma could not name it), or "... imported as local copies" with why: "This library is not connected to this project. To connect it, import the file again and, on the Libraries step, choose the Use card Brilliant offers for it, or Make it a library." (the user's act), or a reason the next section names. A line starting "Make it a library did not run:" means the user chose that card and the setup could not run; its sentence names the cause and what to do: "Connect Figma to set up this library, then import the file again."; "The project was not ready for libraries when its components landed" (nothing to do, Brilliant sets them up once it is); "A library cannot be set up from here" (this editor has no producer lane for the project: a desktop project that is not published, or a cloud project the account cannot admin; publish it or open it where you can, then import again); "Brilliant could not check which libraries your account already has" (try the import again); "The library exists in your account, but its components could not be added to it or found in it" (the report has the details; import again); "The library could not be created from the imported components"; "Figma named this library by a different file than the import screen did" (import again); "The library could not be created in the account that owns this project" (a team project needs a team admin).
- **Library components kept as copies**: for each connected library, the components that did not join it, grouped by reason, each group naming its components. The reasons, and what helps:

  | Reason heading | What it means | Remedy |
  |---|---|---|
  | Differ from the library | The copy changed after the library was made; two differing snapshots are never merged. When the difference is a nested component swapped for another, a row under the names says which for which: `Card: its layer "Icon" is IconB here and IconA in the library.` ("another component" where a side could not be named). Such a copy keeps its own nested component; a link never repoints it. | Import the library's own Figma file (the moment everything converges), or keep the copy. |
  | Could not be compared with the library | The library's version could not be read at the time. | Import the file again. |
  | No exact match in the library | Layers or options with no counterpart in the library. | Keep as copies, or edit the library and release, then import again. |
  | Not in the library at the release this project uses | A newer release may hold them. | `update_library` to the latest release, then import the file again if copies still stand. |
  | The library could not be read | The library could not be opened at the time. | Import the file again. |
  | Share a name with other components | Several library components carry this name. | Rename in the library, release, import again; or keep the copies. |
  | Share a name with library components that differ | Two library components per name, neither matches. | Same as above. |
  | Pages not updated | Pages that could not be opened during the update keep their copies. | Import those pages again. |
  | Other notes | Free-form notes. One is the tidy-up note: "Tidying up for library \"@me/kit\" stopped after 10 min, so 3 copies the linking no longer needs stay on the Components canvas. Import the file again to finish, or delete them." (the links made stand; the leftover copies name no component, so nothing reads as a copy because of it). | The user imports the file again, or, on their word, you delete the leftover copies it counts on the Components canvas (read that canvas first; a master that still has instances is not a leftover). |

  When only overrides and notes stand (no component kept as a copy), the section's heading reads **Library setup** instead. A card titled "<library>: overrides not kept" (or just the library's name under that heading) lists the overrides a pairing dropped because the library's version had no place for them (the "N overrides could not be kept" notice): each line names the override, its layer and the placed instance ("Opacity override on Button / Label, in Checkout, Pay button"). You can re-apply one: an `edit` with an `override(<layer>)` row under the instance's id (`blueprint/components`), once the user tells you the value they want, since the line names the layer and the kind, not the value. "Library setup notes" are the setup's own remarks. A card titled "N unused masters removed" names the masters an import's update took off the Components canvas: an earlier import of the file had left them there and nothing in the project used them (a master the user made is never removed). Information: nothing to do.

## "My library is not updating"

What is true by design: a project depends on a library at a **pinned version** and nothing changes until the pin moves (`reference/libraries`). A teammate's work inside the library is invisible until they cut a **release**; an unreleased edit never reaches a consumer, however long they wait. So first read the pin (the manifest) and ask what version the library's release history shows (the user reads it in the library project's Settings, Library section; `reference/libraries/publishing`).

| What you find | What it means | Remedy |
|---|---|---|
| The pin is older than the latest release | Nothing is wrong; the project waits for someone to move the pin. | `update_library {library: "@acme/design-kit"}` moves it to the latest release (or `version` for a specific one; an older version reverts). The act waits for the download and its answer names any override that could not be kept. The user can do the same from the library's rail row (the update dot, "1.4.0 available", "…" then Update, or the "Libraries" chip's **Update all**), with the review screen first (`reference/libraries/updating`). |
| The pin is the latest release | The library IS current; what the user misses was never released, or lives on a canvas they are not looking at. | Nothing to update. If the library's author is the user, they release from Settings (or you run `create_library_release` on that project when it is open on screen). |
| `.meta.json` is missing, or its `version` is below the pin, or the log says `fetch deferred` | The download did not land: offline, access revoked, the library deleted, the sign-in expired, or the address now belongs to a different project (`reference/libraries/unavailable`). Placed components keep their last look meanwhile. | Nothing you run forces a fetch, but it retries by itself (15 s, 30 s, 1 min, 2 min, then every 5 min) and lands on the next trigger. The user presses **Try again** on the library's banner in the Assets view, signs in again when the banner asks, or, for a replaced library, removes it and adds it again (`remove_library` then `add_library`; in that replaced case alone the remove also deletes the copy and cannot be undone, so say so first; an ordinary remove keeps the copy and the user has an Undo). |
| The manifest entry has `path:` | A folder library is live and has no versions: its folder's current state is what the project gets, re-synced on every save in that folder. | Nothing to update. The user edits the folder (or its author releases it as a library and the project switches to the published one: the "Publish it as a library" fix, `reference/libraries/publishing`). |
| The update landed but a canvas still looks old | In a project saved in a folder, canvases that were not open converge in the background right after the update; elsewhere a closed canvas converges when it is opened. An instance the user changed keeps its override, by design. | Open the canvas (the user), or `read` it: a row that still differs from the master is an override. **Reset overrides** on the instance (the user, in the inspector) makes it follow the release again, size included. |
| The notice said "update removed the color accent" or "update removed the brand" (an agent reads "no longer has ...") | The release removed a token or a brand the project used; the components keep the value they were saved with, nothing goes blank. | Nothing to repair in the project. The library's author restores the token, or the user rebinds those layers to another token (`design-systems/apply`), or `update_library {version}` goes back to the release that still had it. |

## "My component is not linked"

Read the canvas first; the row says which case it is.

| What you find | What it means | Remedy |
|---|---|---|
| A `comp(...)` master in the project and plain `inst(Name)` rows | The component is a **copy** that lives in this project. It never updates from a library because it is not from one. | For copies a Figma import made, the pairing runs from the import's Libraries step, never from an agent act: the user imports the file again and picks the library (`reference/canvases/figma-import-help`). For anything else, place the library's component from the Assets view (the user) or write a fresh `inst(Name, lib(handle/project), canvas(Path))` row at the same `p()` and size, then delete the copy's instance; there is no command that swaps a placed component for another. |
| An `inst(..., lib(...), canvas(...))` row and the `edit` answered that the library "is not in this project" | The library is not declared in the manifest, so the row landed as an empty placeholder that keeps the reference (`reference/libraries/using`). | `add_library {library: "@acme/design-kit"}`; the placeholder fills in by itself once the download lands, and a second `read` confirms it. |
| The `edit` answered "is not downloaded yet" | The library is declared and still on its way. | Wait, then `read` again. If it never fills in, read the log for a `fetch deferred` line and treat it as the "not updating" table above. |
| The `edit` answered "Canvas … is not in @acme/design-kit 1.2.0" or "Component … is not on canvas …" | The path or name is not in the pinned release (the answer lists what the release does have). | Write the row again with a real canvas and component (an id when several share the name), or delete the placeholder. A component that exists only in a newer release: `update_library` first. |
| The inspector reads "This component's library, Acme Design System, was removed from this project." | The library left the manifest (removed here, or the component was pasted from another project). The component keeps its look. | `add_library {library: "@acme/design-kit", version: "<the version it was on>"}`, the same thing the inspector's **Add it back** button does in one press (it picks the version the project last used, or the one the component was copied at). |
| The inspector reads "Button is no longer in Acme Design System 1.4.0." | The release removed that component; the instance keeps its last look and stops updating. | `update_library {library, version: "1.2.0"}` goes back to a release that still has it (the inspector offers **Go back to 1.2.0** in the session the update happened); otherwise the user keeps it as is, or replaces it with another component. |
| The inspector reads "cannot be reached. You may not have access, or it may no longer exist." | A fetch problem, not a canvas problem. | The "not updating" table above. |
| The inspector reads "Canvas \"X\" is not in <library> <version>. Its canvases: ..." | The row's `canvas()` names a canvas the release does not have; the library itself is fine. | Write the row again with one of the canvases named, at the same `p()` and size, then delete the placeholder. |
| The user wants the component to stop following the library | | `detach_component` with its `ids` turns it into a regular frame that looks the same (`reference/libraries/using`). |

Changing the library's own files from the consumer project is never the remedy: a `ds` fence or a file write addressed at a library's styles or canvases is refused ("This is part of Acme Design System (@acme/design-kit). Library components can only be changed in the library project. Nothing was written."). The change goes into the library project, followed by a release there and an update here.

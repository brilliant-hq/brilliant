## "I cannot publish" or "I cannot release"

The refusal sentence names the cause; this is what each one needs.

| The answer | What it needs |
|---|---|
| "Only the owner or a team manager can share this project as a library." / "… can stop sharing this library." / "… can release this library." / "… can change this project's description, display name, topics, license or attribution." | The user is an editor, not the owner or a team manager. Nothing you run changes that: the owner or a manager marks, releases or sets them (`reference/libraries/publishing`). "… can be changed once its cloud settings have loaded. Try again in a moment." is not a role: the published project's settings had not loaded in this session yet; call again. |
| "This project is not synced to Brilliant cloud: publish it first (library acts need the cloud project)." | The project lives only on this computer. The user publishes it from Settings (the pane's one press publishes, marks and releases together when they use **Release new version** there); you have no one-press publish of the open project. Then `mark_project_as_library` and `create_library_release`. |
| "This project is not a library: run "mark_project_as_library" first." | Run it, then release. A project whose every component is an imported copy adopts them as its own at that moment. |
| "Not released: this project has changes that are not synced yet …" or "… Your latest changes have not been saved yet. Try again in a moment." | The release waits for the user's latest edits to reach the cloud, so it never snapshots an older version. Wait a moment and run `create_library_release` again; if it keeps refusing, the user is offline or a save was refused. |
| "Versions only go up. The latest is 1.4.0." / "Versions look like 1.2.0." | Pass a higher `x.y.z`, or no `version` (the default is the next patch; `1.0.0` for a first release). |
| "Release notes can be up to 10,000 characters." / "Descriptions can be up to 280 characters." / "The attribution text is too long. It can be up to 10 KB." / "… is too long. Topics can be up to 30 characters." / "That license is not on the list. Choose one of: …" | Shorten `notes`, `description`, `attribution` or the topic, or pass a license by name or slug (CC BY 4.0, MIT, Apache 2.0, OFL 1.1, All rights reserved, Custom); nothing is cut or written for you. |
| "There is nothing to release yet." | The project has no checkpoint on the cloud yet: the user saves and lets it sync, then release again. |
| "Your session expired. Sign in again to continue." | The user signs in. |

A release that went through says "Released 1.2.0 (checkpoint #N)"; "what versions does this library have" or "did my release land" is `library_releases` (`{library: "@acme/design-kit"}`, or no argument for the project on screen): the versions newest first with their dates and notes, the latest, and the version this project pins, nothing written. The component previews and the index that lets Figma imports recognize the library follow in the background ("Previews for 1.2.0 are ready"), and on the web the tab must stay open for them. Visibility is the project's, not the release's: a public project's library is public, a private project's library is usable by the people who can see the project. The user changes it in Settings (Visibility), where making a released library private asks once ("Projects that use it will stop getting it. Components already placed keep working."); you can run `set_project_settings {visibility: "public" | "private"}` on the project open on screen, which asks nothing, so say that same consequence in the conversation and act only on the user's yes. A public project that uses a private library gets one warning ("This project uses a private library"), never a block.

## "The star or the Private chip is wrong"

- **Stars are per account.** The star on a library's card and page is a button: pressing it stars the library with the signed-in account, the count moves at once and settles on the server's number; pressing again removes it. Signed out, the press asks the user to sign in first. Switching accounts shows that account's stars the next time the Assets view opens, so "I starred it but it is empty" after an account switch is expected. A star that could not be saved (offline) rolls back with "Could not star Acme Design System" and the reason. When the server reports no star count (an older server), no star is drawn at all. There is no agent command for stars; the user presses it (`reference/libraries/adding`).
- **Private, Public and Verified chips read the library project as it is now**, from the server's release listing: a library the owner made public reads Public wherever a Public chip is drawn (the library's page, the update screen, the Figma import's Pick a different library list) and in the words leading a Yours row's subtitle on the Add page ("Public · @acme/kit"), whatever it was when it was added, and Verified stands for Public (no second word). Three places draw no Public chip at all: the Public tab of Add library (the tab already says it), the Use your library card of the Figma import's Libraries step, and the "This looks like a copy of" band of its Project step; there a public library shows nothing (or Verified), and only a private one shows Private. A chip that lags shows the last answer the app holds; it is asked again when the user signs in or out, switches project, or opens the Assets view again. A private library is never shown as Verified, and Verified cannot be requested: it is Brilliant's own list.
- **A chip the user thinks is wrong because the visibility IS wrong** is a settings change on the library project: the owner's Visibility switch in Settings, or `set_project_settings {visibility}` when that project is the one open on screen (the act refuses a project that is not), on the user's word.
- **The Home tile badge** reads "Public library, latest 1.4.0" (or Private library, Verified library, and "…, no releases yet" before the first release) and only on a project marked as a library (`reference/ui/home-projects`).

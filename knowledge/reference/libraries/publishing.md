# Publishing your own library

Any project you can admin becomes a library from **Settings, Project tab, Library section** (the section reads the same whether the project is published yet or not). Releasing, marking a project as a library, and changing its topics or license are for the project's owner or a team manager (see "Who can do this" below).

- **Use as library** marks the project as a library. Turning it off on a library that already has a release asks once first ("Stop sharing Acme Design System?", by the library's name; the palette command "Unmark Project as Library" asks the same way, and the question only acts on the project it was asked for): projects that already use it keep working on the versions they have, and no new releases can be made until you share it again. A library with no releases yet turns off without asking.
- **Topics** appear once marked: pick up to five from the suggested pills (UI kits, Icons, Design systems, Illustrations, Templates, Wireframes, the same labels Browse shows) or type your own (cleaned up for you: "My Kit!" is stored as `my-kit`, shown capitalized; a sixth topic or an empty one is ignored, and one over 30 characters is refused: "… is too long. Topics can be up to 30 characters."). Applied topics show as filled pills with an X to remove; suggestions are quiet pills. The canonical topics are the Add page's Filter by topic menu; free-form ones remain searchable.
- **Release new version** opens the release pane: a computed summary of what changed since the last release (components and variants added, removed, or changed; token changes per brand), a suggested version you can override (a removal, a rename, a move to another canvas, a removed variant option or a removed token suggests a major bump; any addition a minor; content-only changes a patch) with one line under the field saying why it was suggested ("Suggested: major, because 1 component was removed and 1 was renamed."; a component whose canvas was renamed, or that was dragged to another canvas, reads "Button moved to Forms" and counts as "moved to another canvas", which is also a major change because projects that placed it name its canvas), and a notes field that starts empty and is entirely yours, with an **Insert summary** link that writes the change list into it as text you can edit (it adds to what you already typed, never replaces it). Notes can be up to 10,000 characters and are kept whole; longer notes are refused, never cut. A version is three numbers like `1.2.0` ("Versions look like 1.2.0." otherwise) and must be higher than the latest release (the refusal names it: "Versions only go up. The latest is 1.4.0."). The summary is visual: a changed component shows how it looked in the last release, an arrow, and how it looks now; an added component shows its picture with a plus mark, a removed one its last released picture (dimmed) with a minus mark, and a renamed one its picture with the old and new names. A changed color token shows its old and new color swatches, an added or removed color token one swatch; other tokens stay as text. Pictures load in the background and a picture that is not available shows as a quiet empty plate; the notes become the changelog consumers read when updating. The first release defaults to `1.0.0`. If your folder has not finished syncing to the cloud, the release refuses ("Some local changes have not finished syncing. Wait a moment, then retry.") so a release always snapshots exactly what you approved. A release also waits a moment for the edits you just made to reach the cloud before it is cut; if they cannot get there (offline, a save refused) it answers "Your latest changes have not been saved yet. Try again in a moment." and releases nothing. The server keeps the same promise on its side: before it cuts the release it makes sure the cloud copy holds every edit you made, and when it cannot confirm that in time it answers the same sentence instead of releasing an older version, so a release never quietly leaves out your latest work. A refused release shows one notice, replaced by the next refusal, never a stack.
- On a project that is **not published yet**, the pane says plainly that releasing will first publish the project to your account: one press publishes, marks the project as a library, and cuts the release in a single act.
- After a release, the library also sends a small **index** of what it holds (the published Figma keys of its components and, for each component, its name, its variant properties and a structural fingerprint of the Figma design it came from, never its content). The index is what lets a later Figma import recognize the library and offer to link it; it is built once at the moment of the release and sent quietly, and a release made offline sends it the next time the project opens (in the web editor the tab must stay open; a closed tab's index goes with the next release). A library released before this existed is not recognized until it is released again (Brilliant re-indexed the kits it hosts).
- After a release, the library's component previews are made in the background and sent with it ("Previews for 1.2.0 are ready"). If the connection drops or the server is busy, nothing is lost: Brilliant keeps trying quietly and picks up where it left off the next time the project opens; a refusal that will not pass reads "@acme/kit 1.2.0 previews weren't made". A release carries up to 2000 previews; a larger library says how many are covered ("Previews for 1.2.0 cover 2000 of 2340 components") and the rest are drawn when someone opens the library. A release made in the web editor gets its previews the same way, as long as the tab stays open while they are sent: if it is closed first, that release has fewer previews (people who use the library see them drawn on their side instead) and the next release makes them all again.
- **What a release counts as the library's components.** Components the project itself owns. A component that landed in the project only as a copy of another Figma library's component (an icon library the kit used; see "Foreign masters" in `reference/libraries/figma-projects`) is left out of what consumers browse, the component count and the release summary, though instances of it keep working. The exception is a project whose every component is such a copy (a file imported as copies): the moment it becomes a library, by **Make this a library** at the end of an import, by **Use as library** here, or by the palette or agent command, it adopts those copies as its own, so its first release carries them as components other projects can browse, link and match.
- **Verified** is a seal beside a public library's name (on Browse cards, the Add page's rows, library pages, the update screen, the Figma import's Libraries step, and in words on the Home tile tooltip, "Verified library, latest 1.4.0"): a library on Brilliant's verified list, today Brilliant's own kits. A private library is never shown as verified, and the seal is granted by Brilliant, not requested.
- The **release history** lives in the same section, collapsed by default. A release that Figma imports cannot suggest says so on its row: "Not matchable" when it has no index (released before indexing existed, its index not sent yet, or refused), or "3 components not matchable" when some were left out, and the release raises one notice ("Figma imports won't suggest Acme Kit 2.1" when its index was refused, "3 @acme/kit components won't match imports" naming up to five of them when some were left out).
- **Who can do this.** Marking a project as a library, turning that off, and releasing are offered only to the project's owner or a team manager. If you can edit the project but are not one of them, the Library section shows one line instead of its controls: "Only the owner or a team manager can share this project as a library or release a new version." The palette commands answer "Only the owner or a team manager can do this". What an agent reads (`create_library_release`, `mark_project_as_library`, `unmark_project_as_library`) names the act it asked for: "Only the owner or a team manager can share this project as a library." for marking, "Only the owner or a team manager can stop sharing this library." for turning it off, and "Only the owner or a team manager can release this library." for a release. On a project that is not on the cloud yet the section reads "Publish this project first" and an agent reads "This project is not synced to Brilliant cloud: publish it first (library acts need the cloud project)."; an agent has no one-press publish, so the user publishes from Settings first. An agent's `unmark_project_as_library` never asks the stop-sharing question.
- **A first release that makes the project public says so.** On a project that is not published yet and will be published publicly, the release pane reads "This will be public" just above the Release button, with "Releasing will first publish this project to your account. Anyone will be able to see it and use it." and the license it will be shared under ("License: CC BY 4.0 (default)", or the one you chose in the License section). Pressing Release is the consent. If you chose Private in Visibility first, the pane says only that releasing will first publish the project.
- **Making a released library private, or unpublishing it, asks once and says what it costs.** The usual confirm for Private and for Unpublish gains one more sentence when the project is a library with at least one release: "Projects that use it will stop getting it. Components already placed keep working." There is no second question. A library with no releases, and a project that is not a library, read as before.
- A collapsed **License** section in the release pane holds the license dropdown (CC BY 4.0, MIT, Apache 2.0, OFL 1.1, All rights reserved, Custom) and an attribution text box. Untouched, public libraries are shared under **CC BY 4.0** (a quiet line in the pane discloses this), and private ones stay all rights reserved. Consumers read license and attribution on the library's screen in the Assets view; no badge is added anywhere else.

A library's Browse card shows the project's **cover** as it looked at the release (see `design/covers` for designing one), and a library-marked project wears a small stacked-layers badge on its home tile; hovering the badge reads "Public library, latest 1.4.0" (or Private library, Verified library; "…, no releases yet" before the first release). Producer actions need a signed-in account that can admin the project; they work for synced folders and for projects opened from the cloud alike. Agents can drive the whole producer side from the chat or over MCP (see `blueprint/commands`): `mark_project_as_library` / `unmark_project_as_library`, `create_library_release {version?, notes?}` (the notes are the release notes consumers read), `set_project_settings` for the visibility (`public` or `private`) and for what the Libraries page shows (`description`, `displayName`, `topics`, `license`, `attribution`), and `library_releases` to read the release history. A description typed in the desktop app's settings, on the web project page or by an agent is the same field: the last write wins.

## Libraries that use libraries

If a library depends on other libraries, those come along automatically at the versions the library pinned; you never list them in your own manifest. Adding such a library says so once: "Also brings Acme Icons 0.9.0". In Assets, each library's row lists what it brings, also when several of your libraries bring the same one. A component placed from a library shows the components nested in it from those other libraries at the version your project uses, right when you place it. If you also depend on one of them directly, **your pin wins** everywhere, and one note says so: "Two libraries want different versions of Acme Icons. This project uses 1.0.0 everywhere." Chains resolve up to three levels deep (a deeper link is skipped quietly), and a circular dependency is skipped, never followed: "Acme Icons uses Acme Design System, which already uses Acme Icons. That link is skipped; everything else works as usual." A transitive library that cannot be reached degrades exactly like a direct one: last-fetched content keeps rendering, loudly.

## Publishing a project that uses libraries

Publishing warns, it never blocks:

- All dependencies public: nothing is shown.
- A **private** library inside a public project: "Public project uses private <name>" ("Viewers see its components frozen as they are now."): people viewing the project see its components as they are now, without later updates. The same warning appears, wherever the project lives (a folder, a cloud project open in the desktop app, the web editor), the moment you add a private library to a public project or make a project that uses one public. It never stops the add or the change.
- A **local folder** library: "Viewers can’t get “<name>”" ("It’s a local folder. Publish it as a library."; the project publishes either way), with a one-click fix, **Publish it as a library**, that shows "Publishing <name> as a library" while it works and then publishes that folder as a library, gives it version `1.0.0`, and switches your project to it in one step ("Folder library published"): the manifest entry becomes its `@handle/project` form and every component you already placed from the folder, and every place that uses one of its design systems, now points at the published library, with your overrides untouched. It is all or nothing: if any canvas cannot be switched, nothing changes and the message says which one. A folder that is already a synced cloud project keeps that project and gets its next version instead of a second copy. If the folder library uses folder libraries of its own, the message names them, since other people cannot get those. If a step fails, the message names the step in plain words.

The publish goes ahead either way; a warning never holds it, and dismissing one changes nothing.

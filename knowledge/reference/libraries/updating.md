# Library design systems and updates

## Library design systems

A library's brands surface alongside your own, named by the library's handle:

- `@acme/design-kit` is the library's default look; `@acme/design-kit/marketing` is its `marketing` brand.
- They appear in the inspector's brand dropdown and work in Blueprint `ds()` refs, for example `ds(@acme/design-kit, theme(dark))`. A folder library's brands use its plain name: `kit` and `kit/marketing`.

A library brand always resolves against the library's own tokens, never a copy merged into your project, so a library update updates the look everywhere it is used. A release that only changes a token's value re-themes what you placed as soon as you update. That covers every kind of token: colors, corner radius, spacing (auto layout follows the new gap and padding), stroke width, opacity and type. While a library's styles cannot be read (it is still downloading, or you are offline) its components keep the look they had; they never borrow a token of the same name from your project. This works the same in the web editor.

If an update removes something a canvas of the project uses, open or not (a canvas that is not open is read from its saved copy, right after the update lands), it says so in a notification, "Acme Design System update removed the color accent" with "2 components keep their last look." under it (or "...removed the brand marketing" with "Canvases that used it now use its default look."), and in the answer an agent gets: "Acme Design System no longer has the color accent. 2 components keep their last look." (a corner radius, a text style, or "the token X" for other kinds; for a brand, "Canvases", "Layers", or both, "that used it now use its default look"). Nothing goes blank: a component bound to a removed token keeps the value it was saved with, and whatever was set to a removed brand shows the library's default look. Removals that nothing in the project uses are not mentioned.

## Updating and reverting

A dot and the newer version on a library's row in the Assets tab mean a newer release exists (Project settings > Libraries offers **Update all** when more than one library has an update; it updates each to its latest release without a review). The row's **…** then **Update to 1.4.0** (or **Update to 1.4.0** in the library's sheet header, or on the library's own page) opens the library's screen: the library's name with its handle under it when it differs, its Verified, Private or Public chip, and on the right the version you are on and the one you are about to move to ("1.2.0 → 1.4.0", released on its date). That pair is the version picker: press it to choose any release (dates and the "current" mark are listed), and the screen re-computes. The screen is a **review of what the chosen release does to this project**:

- On top, the promise: "Your overrides are kept. If a component changed too much to keep one, we show you where." While the check is still running it sits in a neutral tint with "Checking your overrides…" beside it; the green check appears only once the check finished and found nothing. If the changes could not be worked out it reads "Could not check your overrides. Anything that cannot be kept is named after the update."
- **What changes in this project**, with a count ("1 removed, 3 changed, 2 added"; "N tokens change too." when tokens changed, or "No component changes between 1.2.0 and 1.4.0."). Components you have placed that the release removed, renamed or moved to another canvas come first, in a warning box titled "Removed and in use": each with its picture, "N on canvas" (and "M more on other canvases"), and **Show on canvas** (they keep looking as they do now and stop updating); "N removed, not used in this project." closes the box. Then **Changed**, each with its picture before and after and how many you have on canvas (or "not used in this project"), then **Added** ("New in 1.4.0"). In a project saved in a folder, counts cover every canvas and appear once all have been read ("Counting…" until then; "N canvases could not be read and are not counted." when some cannot be). In the web editor or a cloud project they cover the open canvases, and the page says "Counts cover the canvases that are open now."
- Pressing a changed component opens it large ("changed in 1.4.0, N on canvas"): **Side by side** or **Overlay** with an opacity slider, captioned "1.2.0, in this project now" and "1.4.0, after the update", plus arrows that step through your placed instances ("2 of 14", "Checkout, Pay button") with **Show on canvas** for each, **Next changed component**, and the same Update button. **Back** returns to the review.
- Every property of a component follows the new release on the instances you did not change it on: size, hug/fill/fixed sizing, auto layout direction, gaps, padding, alignment, wrap, pins, corner radii, clipping, min/max, effects, opacity, text and text styles, fills and strokes, a layer added or removed, layer order, and a nested component swapped. An instance you resized keeps its size; an instance you changed in another way keeps that change. An override keeps its whole group: change a gap, padding or corner radius on an instance and its layout stays yours (named "Layout override"); change a text's words and that text keeps its style too; sizing mode, min/max and pins are one "Size" group. A hug axis follows its content, never the master's size. An "Overrides kept" section lists each one by name ("Size override on Card, in Page, Card A") with Show on canvas, for the components the release changed. Reset overrides on an instance makes it follow the release again, size included. Visibility, rotation and flips, shape geometry and the component's own design system follow too.
- If an override cannot be kept (the new release no longer has the layer it was on, no longer offers the variant you chose, or no longer has the slot you put content into), the promise turns into a warning ("Your overrides are kept, except 1 that cannot be. It is listed below.") and a section, "Overrides that cannot be kept", lists each one by name ("Opacity override on Button / Label, in Checkout, Pay button"; a variant reads "Variant choice on Card, in Checkout, Pay button") with Show on canvas. Content you put into a slot that the new release removed is listed the same way ("What you put in Body on Card, in Checkout, Promo card"). The check also reads components nested inside the ones you placed. After the update a notification ("1 override could not be kept", "N overrides could not be kept") names each one (up to five by name, then "and N more"); a nested component on a canvas that was not open is only named after the update.
- Under the review and the Update button, the **release notes of every release in between**, newest first, each under its version and date ("Notes for 1.3.0 and 1.4.0", or "Notes for N releases", scrolls to them; "Release notes you are leaving behind" on a revert; "No notes for this release." when empty). A License row sits at the bottom when the release names a license; when it has an attribution, press the row to read it.
- The review is help, never a gate: the page opens at once ("Working out what changes…" while it reads the release), and if it cannot be worked out it says so ("Could not work out what changes. You can still update.") with **Try again** and you can still update. Updating does need the list of releases: while it loads the header reads "Loading releases…", and if it cannot be read the page says why and the button waits. The review works the same in the web editor.

Press **Update to 1.4.0**; picking a version older than your pin turns the button into **Revert to 1.1.0** and the notes shown are the releases you are leaving behind. Choosing the version you already use reads "This project already uses 1.2.0." and the button waits. Either way:
- The pin in `libraries.yaml` changes, the new version is fetched, and every instance re-syncs.
- **Your overrides are kept.** If a component changed too much to keep one, the review shows you where before you update, and a notification names each one after. That notification comes from the update itself, so it appears whichever way the version changed: this page, **Update all**, **Go back to**, an agent's `update_library` (whose answer names them too), a collaborator's update arriving, a change to the libraries file, a folder library saved, or a canvas opened later. In a project saved in a folder, overrides lost on canvases that were not open are named in the same notification; elsewhere (a folder library, the web editor, a cloud project) a closed canvas converges when it is opened and names its own losses then. The agent's answer names them with one sentence per kind: "N overrides could not be kept (the layer is gone from 1.4.0): …", "N variant choices could not be kept (1.4.0 no longer offers them): …", "Content in N slots could not be kept (the slots are gone from 1.4.0): …" (singular forms for one).
- A component nested inside a library component follows its own component in the same update, at any depth, and keeps the overrides you made on its layers.
- Content you put into a slot stays when the new release keeps the slot. When the release removes the slot, the content goes with it, and both the review and the notification name it.
- Going back to an earlier version (or a later one that brings a layer back) restores that version's layers at the library's values; an override that was lost with a removed layer does not return.
- One notification summarizes what changed on the open canvases ("Acme Design System updated: 3 components changed", with their names), beside the act's own "Updated Acme Design System to 1.4.0", and an open Assets view refreshes itself immediately.
- An update is not an undo step. Cmd+Z after an update undoes your last edit before it, and the component stays on the new version (to go back, pick the earlier version on the library's screen).
- Canvases that are not open are updated in the background right after the update (a project saved in a folder, a published library), one at a time, so no canvas keeps the old look in its file. Only canvases that use the library are touched, and opening a canvas that is already current does not change its file. For a folder library, in a cloud project with no folder and in the web editor, a canvas that was not open is updated when it is opened.

The same screen is where a library's **license and attribution** are shown (the License row at the bottom).

If your sign-in has ended, adding, updating or releasing a library answers "Your session expired. Sign in again to continue."

# Top Toolbar

In the desktop app one bar runs across the top of the window: the **home button**, one **tab per open project** in your saved order (each tab is the bar's full height, with a thin divider between tabs, and the tab you are on joins the panel below it), then **+** for a new project; at the right end, the **Focus / Full** switch, the people working on the project with you, the notifications **bell**, **Share** (**Sign in** when you are signed out) and the zoom readout. In AI focus (Focus) the right end shows only the Focus / Full switch; notifications still pop up as usual. In Focus the tabs and **+** give way to a file switcher after the home button: the name of the file you are on with a chevron, then one small bar per agent working in this project, in that agent's colour, tall when it works on this file and short when it works on another file of the project (from six agents on, five bars and a count). The name and chevron never move as agents come and go; hover the bars to see who works where. Click the name or the bars for the menu: **Agents working** (the files agents are editing, with their bars; choosing one opens it and, if its agent's work is off screen, moves the view there once, without following it after), **Files** (your five most recent, opening where you left them) and **Search files** (Cmd+P). The file you are on is checked. Click the home button to see every project tab again and switch projects there (Ctrl+Tab still cycles them); each project keeps its own Focus or Full. There is no breadcrumb: the project's name and who can see it are in the left panel's project header (`reference/ui/left-toolbar`), the canvas you are on is the selected row of the Files tree, unsaved changes show as a dot on the tab, the canvas copy rows (Copy Canvas Path, Copy Canvas URL, Copy Link to Selection) are in the project header's menu and the canvas and Files right-click menus, and checkpoints are made and browsed in the rail's **Checkpoints** tab. Tabs, their badges, their menus and their shortcuts work as described below.

- **Tabs**: click one to switch projects, middle-click (or its ✕) to close, drag to reorder. The tab you are on always shows its ✕; other tabs show theirs on hover. **Cmd+W** (Ctrl+W on Windows) closes the tab you are on while the AI chat is closed; while the chat is open (or its input has focus) Cmd+W closes the chat instead, and on the home screen it does nothing (home never closes). Hover a tab for its full name, where it lives (the folder, with your home folder shown as `~`, or its brilliant.design address), and, on the tab you are on, the Close Tab shortcut. Each tab reads `project / canvas` and shows the project's current canvas; a shimmer marks an agent working there right now. An agent in Brilliant's own chat clears it the moment it finishes (nothing lingers on the tab afterward). An external agent connected over MCP (Claude Code, Cursor and the like) lights the tab of the project it edits too, in its own color, and hovering the shimmer names it ("Claude Code (MCP) is editing"). An external agent never tells Brilliant it is done, so its shimmer stays for a while after its last call: about a minute and a half after its last edit, about 15 seconds when it only read. The home button opens the project home screen.
- **Rename a project from its tab**: double-click the tab **title** (or right-click the tab and choose **Rename**) to rename the project without going back to the home screen. The title turns into an inline text field with the current name selected; type the new name and press **Enter** to confirm, **Escape** to cancel (an empty or unchanged name also cancels, and clicking away confirms). Your typing is kept while the field is open even if you move the pointer off the tab. The renamed tab **stays exactly where it is** in the strip and stays the active tab, and no other project flashes open while it renames. It renames the project exactly as the home screen's "…" → Rename does: a local or synced project renames its folder on disk, a cloud-only project renames on the web (old links redirect). A **view-only** project (one you can open but not edit) offers no Rename, on the tab or in its menu.
- **Right-click a project tab** for the same menu as that project's "…" on the home screen, minus **Open** (the project is already open) and the list items **Pin to top** and **Remove from list** (pin from the home screen; close the tab instead of removing it), plus **Close Tab**, **Close Others** and **Close to the Right**. In order, as they apply, with a divider between groups: Open in web, Sharing…, Change cover…; Make available offline, Duplicate as local project, Rename…, Show in Finder (Show in Explorer on Windows); then **Close Tab**, **Close Others** (every other project tab) and **Close to the Right** (every tab after this one) after a divider, the last two grayed when there is nothing to close; if the tab you are on is among the closed, the right-clicked tab becomes the active one; then **Delete project…** in red, last, after its own divider. Each item does exactly what it does on home (see "The "…" menu" in `reference/ui/home-projects`). Delete project asks first, with a **Move to Trash** button (**Move to Recycle Bin** on Windows), then closes the tab and moves the folder there.
- **Hover any island control for what it does:** the home button says Home with its shortcut (Cmd+Ctrl+0, Ctrl+0 on Windows), the **+** says New project with **Cmd+Shift+N**, and each tab badge names itself (Cloud project, Synced, Private, View only, Library, or another account's cloud project).
- **The menu bar has the same doors.** **File** starts with **New Project** (Cmd+Shift+N), **Open Project Folder...** (Cmd+O) and **Close Tab** (Cmd+W); **Window** ends with Home and every open project, the one you are on checked; choose one to switch to it. On Windows these are in the menu bar at the top of the window, with Ctrl in place of Cmd. While the file explorer has keyboard focus, Cmd+Shift+N creates a folder there instead (the explorer's own shortcut), and New Project in the menu grays until focus leaves it.
- **A tab carries no storage or privacy badge** (where a project lives and how public it is show on its home tile and row, `reference/ui/home-projects`). A team project's tab leads with the team's small square avatar. While a checkpoint is saving, a sticky "Saving checkpoint…" notification (with a loading spinner) shows the progress; the tab stays put.
- **A project you can only view shows an eye** on its tab, at the tab's right end. Hovering the tab swaps the eye for the close button, and the tab's hover tooltip says "View only: you can look, not edit". It means you can open and read the project but not edit it (a cloud or synced project your current account has no edit rights on; local-only projects are always editable and never show it). It appears and disappears live as your access changes (signing in or out, switching account). What view-only means, and the ways forward, are under "Opening a project you cannot edit" in `reference/canvases/collaboration`.
- **Every project tab shows its own sync trouble at its right end**, the tab you are on and the ones in the background alike. A cloud slash means your changes cannot reach the cloud right now (usually you are offline): they are kept, and Brilliant retries by itself. A red octagon means syncing failed and a notification explains why and what to do. On the tab you are on, an amber triangle means its open canvases use fonts this computer does not have. Hover the mark for the reason in words. **Click the mark** for the project's status list, grouped under **This file**, worst first: **Can't save <project>** with **Retry** (tries again right now; the link shows only when there is something to retry), **Offline · changes kept on this Mac** ("this PC" on Windows) with *Retrying* (nothing to press, it retries by itself), and **<n> missing fonts** with **Replace** (opens the font replacement steps). The mark stays put while you hover the tab and the close button appears after it, so you can click either; nothing on the strip moves when you hover. A project that syncs fine shows none of this.
- **Home is always leftmost**, then your open projects in the order you opened or dragged them into. Switching projects does **not** reorder the strip; the active tab is simply highlighted where it sits. On the home screen no tab is highlighted.
- Every project tab can be dragged to reorder; only the home button stays put.
- **Ctrl+Tab** / **Ctrl+Shift+Tab** cycle the strip, and **Cmd+Ctrl+0** jumps home while **Cmd+Ctrl+1..9** jump to a project. They address your **tab order** (the order tabs were opened or dragged into), which is also the left-to-right screen order, so a given number always means the same project. On macOS Cmd+Ctrl+1..9 only fire when nothing is selected; with a selection the same chord sets rotation. On Windows the jumps are **Ctrl+1..9 / Ctrl+0** and fire with or without a selection (rotation lives on Alt+Shift+digit there).
- When the bar runs out of room, tab labels shorten first, then the oldest inactive tabs fold into a "N more" button at the end of the tabs, before **+**. Home, **+**, the tab you are on and the right end never fold.
- Switching to an already-open project is instant and says nothing. A switch that takes longer than a moment (a cold project, a cloud one over the network) raises a "Switching to {project}…" notification that clears itself the instant the project lands; if it cannot be opened, that notification is replaced by the failure warning. In the desktop bar a switch shows on the tab itself: after about a third of a second a small grey spinner takes the place of the tab's ✕ at its right end (the tab and its neighbours do not move), stays at least half a second so it never flickers, and fades back into the ✕ when the project lands. Hover the loading tab to get the ✕ back: it closes the tab, which cancels the switch. A switch faster than that shows nothing.
- **The bell** at the right end of the bar opens the notifications panel and carries a count of unread ones. It turns **red whenever an unresolved failure or warning is live** (a failed sync among them) and stays red until that is resolved; closing a message does not clear it. **Create Checkpoint** is the **+** in the rail's Checkpoints tab, the project header's menu, or Option+Cmd+S (Ctrl+Alt+S on Windows); it opens the same name prompt.
- Notifications appear under the toolbar. Confirmations and successes ("Link copied") fade after a few seconds, and so does the note that a canvas or text file you have open was changed by another app and reloaded ("Hero page reloaded: changed by another app"), which is not kept in the notifications list; **failures and warnings stay until dismissed**, so a verdict is never lost by looking away. Close one with its x, a click on its body, or Escape. Everything worth coming back to is also kept in the **notifications panel** behind the bell (Needs you, Today, Earlier); its "…" menu offers **Clear read notifications** and **Clear all notifications** (each with an Undo). In overlay mode, where there is no bell, every notification shows as a toast and the island's clear-notifications button clears them. A notification's detail line sits under its title and wraps onto more lines rather than being cut off (a chat reply's preview is the one detail kept to a single line), and when the notifications stack taller than the window, the stack scrolls.
- **What the notifications panel keeps.** The bell's panel is a record of things worth coming back to, not a log of everything the app said. Anything with work at stake keeps a row: a save or sync that failed, an edit kept only on this device, a decision waiting for you, news from other people or the outside world. Three kinds of notice are a toast only and never become a row: a prompt you opened yourself (a confirm such as Unpublish, Revoke or Delete, a name field), a refusal of the click you just made where nothing changed ("Couldn't open that link", "Copy as WebP isn't available on web"), and a condition that clears itself (working offline, live sync catching up, the folder watcher reconnecting), which stays on the canvas or its indicator while it lasts. The panel has three sections: **Needs you** (decisions, and failures still on screen that you can act on, with their buttons), **Today**, and **Earlier**.
- **Clearing the panel.** The panel's **⋯** menu has **Clear read notifications** and, right under it, **Clear all notifications**. Clear all removes every row, read or unread, except the ones under **Needs you** and failures still on screen, and also closes the short-lived toasts showing ("Link copied"); a failure that is still held and a decision waiting for you stay. A toast "Cleared N items" offers **Undo** for 8 seconds. Each item is greyed out, never hidden, when there is nothing for it to clear.
- **Notification rows read whole.** In the bell's panel a notification's title and detail show up to two lines each. If a row is still cut off, click it to expand it in place to the full text; click again to fold it. Clicking a row marks it read. Unread rows carry a blue dot and darker text (the title weight stays the same). A row keeps its buttons after its notice has gone when the part of the app that raised it can still do the action; a button that can no longer work is not shown.
- **Website activity in the notifications panel (desktop).** While you are signed in, the bell's panel also shows what happens to your work on brilliant.design. A **team or project invitation** sits under **Needs you**; clicking it opens the invitation in your browser, where you accept it. Everything else (follows, stars, forks, and new publishes from people and teams you follow) collects at the bottom in one quiet **Social** group, folded into a single row that says who and how much ("Jonas Albrecht, Mia Chen and 17 others" over "13 follows · 5 stars · 1 fork · 1 publish"). Click that row, or the chevron beside "Social", to open the group: each row reads the same as on the website ("Kai and 2 others followed you") and opens its page in your browser. The whole Social group counts as one on the bell's badge. **Mark all read** marks your website notifications read too (on the website as well). Opening a single row marks it read in this session only; the website keeps counting it until you mark all read. The panel asks for new activity when it opens and about once a minute; signed out, the Social group is not shown, and if Brilliant cannot reach the server the group is hidden until it can, rather than showing an older list.
- **Long work shows on its project's tab, not as a floating notification.** While something takes real time (a paste, an image upload, a publish, an export, duplicating or downloading a project, a Figma import), the project's tab shows a small progress ring at its right end. Click it for the status list: each running job has a row in its own words with a thin progress line and **Cancel** when it can be stopped, under **This file**, or under **App** for work that is not about one project (a Figma import, a Brilliant update download). If the tab also has a problem, its warning mark takes the spot and the same list holds both. Notifications only tell you how the work ended: done (with an action such as **Show in Finder**, for about 5 seconds) or failed (kept in the bell until you see it). A done job also stays in the bell when it ran longer than a few seconds, or when it finished while you were looking at another project or another app. Switching to a project shows as the tab's own spinner (above), and its row in the list appears once it takes longer than about a second; saving a checkpoint shows on the tab only when it takes longer than about a second, and the Figma import's progress and "upgrade from Figma" pulls show the same way. With the toolbars hidden, or with no tab for the project, the running job shows as a notification instead.
- **A paste that takes real time says so.** Paste something heavy (a big Figma selection, a whole design pasted from another project) and the tab's progress ring and status row say "Pasting…" with a progress line that fills as the elements land; it names the stage it is in when there is one ("Fetching images…" while image bytes are downloaded, "Uploading assets…" while a cloud project stores them), and finishes with a brief "Pasted". A paste that lands immediately shows nothing at all, and a paste that fails shows only its own error: never a "Pasted" on top of it. The point is that Cmd+V never looks like it did nothing, so there is no reason to press it twice.
- A notification carrying buttons (a confirm, a conflict, an invitation) is a **CTA notification**. It waits for its answer and **never expires on its own**, whatever its severity: it leaves only when one of its buttons is pressed, or via its x or Escape. Clicking its body does nothing. Where it shows depends on who raised it. A dialog you opened yourself (naming a checkpoint, a publish or unpublish confirm, reviewing a file conflict) stays in view as a toast until you answer or close it, the way a dialog should; so does a notice you type into (a feedback prompt with its message box). An offer or notice the app raised on its own waits under **Needs you** in the notifications panel, ready to be answered later (where there is no bell it shows as a toast and tucks away, and hovering the island brings it back).
- **An update is a card.** When a new Brilliant version is ready, a card under the top bar at the right names it, lists what changed (the first notes, with "Show N more" for the rest), and offers **Install <version>**: it downloads, installs, and relaunches from right where you are, showing its progress on the card. A **What's new** link on the card opens the release notes in Settings > About. Close the card with its x and an **Update** pill stays beside the notification bell; press it to bring the card back (with the interface hidden, the pill stands where the card was). The card comes back on the next background check if you close it, and disappears once you are on the current build. Brilliant keeps checking in the background while it stays open, so a session left running for days still gets the card, and if an even newer version ships while it is up, the card names the newer one. Checking by hand from Settings > About never pops the card: About shows "Checking for updates…", "You're up to date" or "Couldn't check", or the install card itself when an update exists. On Windows, if an update does not actually install (something on the machine was still holding the app's files), the next launch says so instead of staying silent: a notification reads "Brilliant <version> didn't install. Still on <your version>. Check for updates to retry.", with **Update** as the retry and **What's new** beside it, and the pill reads **Try again**.
- **The update reaches you even when the canvas can't render.** If the canvas renderer fails or is held at startup (any of its cards, such as "Rendering can't start") and a new version is ready, the card itself offers **Update to <version>** as its main button, with the card's own action (Retry, Restart rendering, or Try anyway) and Report below it, so the fix is one click away instead of hidden behind the card.
- **Paid features knock, they don't block.** Hitting a paid wall (a short handle, making a project private, publishing a private drop, a second guest editor, a team whose Team plan lapsed) opens the same sign-in-like page over the editor (the palette shell, canvas dimmed) that states the reason and offers one next action ("See Team plans" or "Create a team" for team features); press Escape or click outside the page to put it away and keep whatever you were doing. Locked paid toggles still show a quiet "Available on Personal" chip, and tapping one opens the same page: the toggle never flips until the plan does. You can also reach the checkout directly by typing **Upgrade** in the palette (the row shows when you are signed in and the session is editable); it opens the same in-editor checkout the walls do.
- A held failure is never taken away behind the user's back. A later result reusing the same notification (a checkpoint that failed, then succeeded) updates the wording but keeps the notification on screen until it is closed, and the `dismiss_notifications` command clears only the transient toasts, leaving failures and pending confirms in place. Clearing failure notifications is the user's call, made from "Clear all" or the **Clear All Notifications** command in the palette (Cmd+Shift+P), which an agent cannot run.
- **Every notification can be closed, a sync failure included.** Closing a sync failure (its x, or "Clear all") takes it off the screen only: it stays in the notifications list and the red dot keeps showing the problem until sync recovers, when it goes away by itself. Closing it also means it does not pop back for the same failure; if sync recovers and later fails again, a new notification appears. Left alone, it tucks away after a few seconds or when you move the pointer away, like any notification.
- **An image that fails to upload retries on its own.** If a slow or dropped connection makes an image upload give up, the app still holds the picture and re-sends it by itself the moment the connection returns, and until then its sync notice offers a **Retry** you can press now. Only a wall a retry cannot clear (out of storage, a file past the size limit, or no access to the project) stops for good, and the notice says so instead of promising a retry.
- **"Some of Brilliant's fonts failed to load"** is a warning the app raises once at startup (Windows and Linux) when the fonts it ships with could not be loaded from its install folder, which is what makes menus and panels render in an unfamiliar system font and toolbar icons render blank. It is not a design problem in your project. The usual causes are an antivirus that quarantined files under the app's `data\flutter_assets` folder, a system font changer or font-rendering hook, or an incomplete install; adding Brilliant to the antivirus exclusions and reinstalling normally fixes it. The notification's button opens the logs folder (`~/.config/brilliant/logs`), where `brilliant.log` carries one `chrome_font_probe` line naming each affected font file and the exact error. When the blocked files are the app's own interface font or toolbar icons, Brilliant repairs itself: it switches to a copy of those fonts and icons built into the app, the interface renders correctly, and the notice reads **"Brilliant restored its fonts from a built-in copy"** instead (an information notice, same button). No reinstall is needed after a repaired start: add an antivirus exclusion for the Brilliant folder so the next start loads the installed fonts directly, and reinstall only if the interface still looks wrong.
- Drag anywhere on the island or the empty strip beside it to move the OS window (disabled in fullscreen / maximized; cursor turns grab/grabbing). Double-click empty strip or island space for the macOS title-bar action (zoom/minimize, per your System Settings).

There is no save chip in the top toolbar: auto-save runs in the background with a ~500 ms debounce. The save-state cue is the dot on the project's tab, shown until the change is saved.

On the web, a tab left open across app updates keeps itself current: if it can no longer load its own assets because a newer version has superseded it, it reloads once onto the current version (landing you back on the same canvas) instead of degrading into a broken editor.

**Sync health is reported by exception only.** A project that is syncing shows nothing at all: there is no standing sync indicator anywhere. Going offline, or a brief disconnect, raises no notification either (only the quiet cloud slash on the project's tab). A notification appears only when your changes have been waiting for about ten minutes while Brilliant can reach the server and sync still fails, or when you need to act: signing in again, an upgrade, storage, or a choice about which version to keep. When one does appear it names the project and the reason in words, and the notification dot goes red. Losing **write access** to a shared or team project is its own honest state, not a sign-in problem: the notification says sync stopped, that your changes are safe on this device, and that the fix is having your access restored (it never asks you to sign in again, and it never spins a retry that cannot succeed). Once access is restored, the held changes push by themselves. A **team project whose team plan has lapsed** reads the same way, naming the Team plan as the fix. That notification **stays in the list while the trouble lasts**: you can close it, which takes it off the screen, but the list keeps it and the red dot is guaranteed to be there for exactly as long as sync is broken. Repeated failures update that one notification instead of stacking new ones. When sync recovers, the same notification flips to "Back in sync" and fades on its own; if no notification was shown, recovery is silent too. If you switch away from a project while its sync is still failing, the notification stays (now naming that project, and now closable, since nothing is retrying it until you open it again). If the server asks Brilliant to slow down (a burst of requests, such as opening a very large project), every cloud request pauses together and resumes on its own once the pause ends, with no notification; saves made in the meantime go out right after, so nothing is lost. So: no red dot means your work is reaching the cloud, or is on its way and safe on this device.

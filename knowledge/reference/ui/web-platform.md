# Web Platform (brilliant.design)

Published projects live at `brilliant.design/{handle}/{project}`. Profiles (`brilliant.design/{handle}`) and the web editor share one persistent GitHub-style shell:

- **Site navbar** (always on top): brand, search (Cmd+K palette), the New menu, and the account menu. It stays mounted while you browse profiles and open, create, or switch projects.
- **Profile tab bar** under the navbar: the OWNER's Overview / Projects / Drops / Stars tabs. Viewing `/{handle}/{project}` shows `{handle}`'s tabs (no tab highlighted while the editor is open); clicking a tab goes to that owner's profile view. Leaving for a profile tab keeps the editor loaded in the background, so returning to the project is instant.
- **The content area** below shows either the profile view or the editor. Canvas deep links (`/{handle}/{project}/{canvasName}`, plus `?sel=` for a selection) open that canvas directly, and the address bar follows as you switch canvases.
- **Links are resilient.** A link keeps working as the project evolves: if the canvas was moved or renamed since the link was made, it opens at its new location (the address bar updates and a small note says so); if it no longer exists, the project's first canvas opens with a note. Selected element ids in `?sel=` that no longer exist are simply dropped; the still-existing ones are selected, or the canvas just fits to content. A link only fails when the project itself is gone or private.

**Pasting into text fields on the web.** Cmd+V (Ctrl+V on Windows and Linux) pastes into any text field with no clipboard permission. The right-click Paste button has to read the clipboard itself, so when your browser blocks that read a one-time note says "Your browser blocked reading the clipboard. Press Cmd+V to paste." (Ctrl+V off a Mac) instead of the button silently doing nothing.

**The editor's own controls in the browser.** The web editor has no top bar of its own: the site navbar above it carries the logo, search, New, the site bell and your account. The project's people, Share and zoom sit in one row at the top of the right panel (the faces of whoever else is here, then Share, with the zoom field at the right). Signed out, that row holds only the zoom field (and the faces when others are live); sign in from the site navbar. When you hide the right panel (Toggle Right Toolbar, Cmd+Shift+→), the same controls float as a small pill in the canvas's top right corner. The editor's notification bell sits at the bottom of the far-left rail, above your avatar: it opens the editor's inbox to the right of the rail (needs-you items, then a folded Social group with the website's notifications). Signed out, the rail has no bell and no avatar. No floating pill names the canvas above it either: the open canvas is the highlighted row in the Files panel, where you double-click its name to rename it, and its link comes from Share or from the copy rows in the canvas's right-click menu.

**Project pages: Canvas, History and Settings.** The editor page itself shows no project tabs in the site navbar: checkpoints and project settings live in the editor's rail, on its **Checkpoints** and **Project** tabs. On a computer the old page addresses open the editor instead, so links in emails and shared URLs keep working: `brilliant.design/{handle}/{project}/history` opens the **Checkpoints** tab, `.../checkpoint/{n}` previews checkpoint n in place (read only; a checkpoint that does not exist opens the list and says so), and `.../settings`, `.../settings/access` and `.../settings/danger` open the **Project** tab on General, Access and publishing, or Danger zone (Danger zone is for the owner or a team admin; anyone else lands on General). The Home project card menu's **History** and **Settings** open the same tabs. On a phone, History and Settings are still full pages, carrying a tab cluster of **Canvas** (back to the project), **History**, and, for the owner only, **Settings**.

- **History** is a filterable timeline of the project's checkpoints: a live-work row at the top, then the saved checkpoints below. Each checkpoint is either one you **named** or an **automatic** one the app saved as it went, so you can filter by named or automatic, filter by author, or search the checkpoint text; expanding a checkpoint shows which canvases changed in it. **New checkpoint** freezes the current work as a named checkpoint, and anyone who can edit the project can create one, not only the owner. The owner can **Restore** any checkpoint, either the whole project or a single canvas, behind a confirmation, and a restore first saves your current unsaved work as its own checkpoint so nothing is lost.
- **Settings** (owner only) is where you **rename** the project (the confirm reminds you that links to the old name keep redirecting until you reuse the name; renaming a project that serves as your profile README removes the README), change its visibility and audience, manage collaborators, and create **share links**. A rename follows the project everywhere it is open: desktop tabs and synced folders pick up the new name live with a small notice, and other web editors re-open in place at the new address.

**Share links** are a read-only door to a **private** project: anyone with the link can view it without signing in, and can never edit. The design's fonts load for these viewers too, so shared text keeps its real typeface instead of falling back to a default. They live in the project Settings page and are a **paid** feature to create (a public project offers none, since its address is already viewable). Each link is a short `brilliant.design/s/...` address you copy, it never expires, and it keeps working **until you revoke it**. Flipping the project back to public, or revoking a link, cuts off that access right away.

**The playground** (`brilliant.design/playground`, no account needed): a scratch editor with the pills in the chat (`reference/ai-setup/replays`). With no AI of your own, picking one replays a real agent session building live on the canvas; everything it makes is a real, editable element. The editor at the top of the brilliant.design home page is the same playground: a prompt you type there runs right there, and its **Open fullscreen** button turns it into the full playground in place. On the playground page itself the button reads **Sign in** when you are signed out and **Save a copy** when you are signed in. Nothing in the playground persists until you keep the design as a project: once you have made something of your own, an offer to keep it waits behind the notification dot on the top island (it does not pop up; hover the island to read it: `Sign in to keep it` when signed out, `Save as project` when signed in); keeping it turns the canvas you are looking at into your project in place (the address becomes `/{handle}/{project}`, nothing reloads, and edits save from then on; on the free plan the project is public). Signed in, an unsaved scratch is also kept on that device for an hour after your last edit, so a refresh or a crash brings it back with a `Restored your unsaved scratch` toast offering `Save as project` or `Discard` (this includes a board opened from **Edit with AI** on the remove-background page: a reload brings back your latest board, never the bare cutout; an image that was still generating when the page reloaded did not finish, and a notice says so); signed out, nothing is kept and leaving the page loses the scratch (the browser warns first). The chat transcript itself is not kept.

**Editing someone else's public project**: opening a public project link lets you pan, zoom, and edit it right away, the same view as before but with the tools live. Your first real change quietly turns the canvas into a local copy of theirs (their project is never written to), and ONE notification, `You're editing a copy`, offers **Save a copy** to keep the copy as your own project (born **private** when you are on a paid plan, public on Free) or **Go back** to drop it and return to just viewing. That is the only notification in this flow. The copy lives only in this browser tab until you save it (a reload loses it, and the browser warns first), and the right-toolbar Share button reads **Save a copy** the whole time (**Sign in** while you are signed out).

**The onboarding walkthrough** is one guided step, the same on the desktop app and in the playground. It runs once per account when you are signed in, or per browser when you are not. It lights two things at once, the pills and the chat box, under one card: `Pick an example to watch, or describe your own.` (with an AI of your own connected the pills are suggestions and it reads `Pick a prompt to try, or describe your own.`) With only Brilliant AI connected, picking a pill replays a recorded session of your agent generating real, native elements (a recording, so it spends nothing); with an AI of your own, a pill puts its prompt in the chat box instead (`reference/ai-setup/replays`). Clicking into the chat box, pressing Tab, pasting, or simply starting to type there (an input method composition counts) ends the walkthrough instead, and the prompt you send runs live as a real Brilliant AI turn on the same canvas, with its status line showing straight away. If Brilliant AI is unavailable and you have no AI of your own connected, the prompt stays on screen with the steps to connect one, and it sends once you do. It appears only on the home screen or the first time you open the regular playground, and sending a message from the inline AI box (the sparkle on a selection) suppresses it for good. There is no skip button on the card and Esc does not close it, but opening a new chat ("+", Cmd+N, or /new-chat) ends the walkthrough at any time; the walkthrough card ends with the window, so the palette (Cmd+Shift+P) and Settings open normally again. A replay never moves the canvas: the design builds where its recording puts it. `Reset onboarding` (palette) re-arms it on every device you are signed in on, or in this browser when you are signed out. It re-arms right away on the device where you ran it. Another signed-in device that is already open picks it up the next time it launches. Every message you type is a real chat on Brilliant AI (or on your own AI if you chose one), and a follow-up typed in a replayed chat opens a fresh real chat on the same canvas.

**The New menu** (the "+ New" button in the navbar, signed in only; on a phone, the New row of the account menu) has three doors, each acting at once:

- **New project**: creates an empty project named `Untitled` (then `Untitled 2`, `Untitled 3`, ... when taken) and opens it in the editor. Its line says who owns it ("Saved under @handle."): the account you are acting as, which you switch in the account menu. When you belong to a team it asks first, in a small dialog with the name and visibility. Rename later from project settings. It is born **private** when you are on a paid plan (for a team project, when the team is), and public on Free.
- **Playground**: opens the playground in this window. No project is created; keep the work as a project if you like it.
- **Import from Figma**: opens the import's start. Paste a Figma file link and press Continue (a link that is not a Figma file says so on Continue), or start from the Brilliant plugin in your Figma file. The import screen opens (in the editor when you are in one, otherwise in the playground) and waits for you to open the Brilliant plugin in that file; the project is created when you press Import on the screen, and the tab becomes it (`reference/canvases/figma-import`). Nothing is fetched by link: the plugin reads the file, so the file's design system and library wiring come across. If your Figma account isn't connected yet, Continue routes through Figma sign-in first and returns you to the import's start with the link preserved. The connection belongs to the account that started it, whatever Brilliant account the returning browser is signed in as; when they differ, the page says which account is connected and you go back to where you started.

The web editor has the same Settings Library section and the same library acts as the desktop app (`reference/libraries/publishing`); a release's previews and its Figma index are sent while the tab stays open.

A profile page's empty-state "Create your first project" card is the same single click: it instantly creates `untitled` and opens the editor (no dialog).

**Account settings** (`brilliant.design/settings`, via the account menu → Settings): the handle editor, and the Danger Zone with **Delete account**. Deletion asks for confirmation twice and requires typing your handle (verified server-side). It removes projects and drops immediately (permanently deleted after a 30-day window, no undo past it), keeps forks other people made of your public work, holds the freed handle for 30 days, and signs you out on every device. An active paid subscription (or being a team's only admin) must be resolved first: the request is refused with a message naming what to cancel or transfer. Returning later means signing up as a brand-new account.
